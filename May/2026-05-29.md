### 강의

1. 데이터베이스 동시성 제어
    - Serial Schedule
        - 트랜잭션을 순차적으로 하나씩 실행한 스케줄
        - 동시 실행이 없어 이상 현상은 없지만 처리량이 낮음
    - 일관성
        - 트랜잭션 전/후 데이터가 무결성 규칙을 만족하는 상태
        - 제약 조건, 비즈니스 규칙 위반이 없어야 함
    - 동시성
        - 여러 트랜잭션을 겹쳐 실행해 처리량과 응답성을 높이는 방식
        - 동시성 증가 시 충돌/교착상태/이상 현상 대응이 필요
    - Conflict 
        - 서로 다른 트랜잭션의 연산이 같은 데이터에 접근하고, 최소 하나가 Write인 경우
        - 대표 조합: Read-Write, Write-Read, Write-Write
        - 충돌 연산의 순서가 바뀌면 결과가 달라질 수 있어 제어가 필요
        - 모든 충돌이 항상 락을 의미하진 않지만, 정합성을 위해 락/격리수준/버전검사를 사용
    - Pessimisitic Lock
        - 충돌 가능성을 높게 보고 먼저 락을 획득한 뒤 작업
        - 장점: 충돌 시 데이터 정합성 보장이 명확함
        - 단점: 락 대기 시간 증가, 데드락 가능성, 처리량 저하
        - 예: 재고 차감, 계좌 이체처럼 충돌 비용이 큰 작업
    - Optimistic Lock
        - 충돌이 적다고 가정하고 락 없이 진행 후 커밋 시점에 충돌 검증
        - 보통 version/timestamp 컬럼으로 변경 여부를 비교
        - 장점: 락 대기 감소, 읽기 중심 서비스에서 성능 유리
        - 단점: 충돌 발생 시 재시도 로직 필요
        - 예: 게시글 수정, 프로필 수정처럼 충돌 빈도가 낮은 작업
2. OAuth
    - 서드파티에서 사용자 리소스에 대한 접근권한을 얻을 수 있게 해주는 프로토콜
    - 인증(Authentication)과 인가(Authorization)를 분리해 비밀번호 공유 없이 권한 위임 가능
    - 주요 주체
        - Resource Owner: 사용자
        - Client: 권한을 위임받아 API를 호출하는 앱
        - Authorization Server: 사용자 인증 후 토큰 발급
        - Resource Server: 액세스 토큰을 검증하고 리소스 제공
    - 기본 흐름
        - 클라이언트가 사용자에게 동의 화면 요청
        - 인가 서버가 Authorization Code 발급
        - 클라이언트가 Code로 Access Token 교환
        - 클라이언트가 토큰으로 리소스 서버 API 호출
    - PKCE
        - 공개 클라이언트(모바일/SPA)에서 Code 탈취 공격을 줄이기 위한 확장
        - code_verifier, code_challenge를 사용해 토큰 교환 요청 주체를 검증
        - 현재 Authorization Code + PKCE 조합이 권장 방식

2. 메인 키워드
    - RDBMS
        - 고정 스키마(정규화), 조인, 강한 트랜잭션(ACID)에 강점
        - 복잡한 관계형 질의와 무결성 제약(Primary/Foreign Key) 처리에 유리
        - 대규모 분산 쓰기/수평 확장 시 샤딩 설계 복잡도와 운영 비용 증가
    - NoSQL
        - 유연한 스키마와 분산 환경 중심 설계로 확장성(scale-out)에 강점
        - 데이터 모델을 용도별로 선택(문서형, 키-값, 컬럼형, 그래프)
        - 초고속 조회/대용량 로그/관계 탐색 등 특정 워크로드 최적화에 유리

4. 결론
    - RDBMS 한계와 NoSQL 사용 이유
        - RDBMS
            - 강한 정합성과 복잡한 조인에 강하지만, 대규모 분산 쓰기 확장은 상대적으로 어렵다.
            - 스키마 변경 비용이 커서 빠른 도메인 변경에 불리할 수 있다.
        - NoSQL
            - 유연한 스키마와 수평 확장에 유리해 대규모 트래픽 처리에 적합하다.
            - 문서/키-값/컬럼/그래프 등 워크로드별 최적 모델 선택이 가능하다.
        - 정리
            - 실무에서는 대체보다 혼용(Polyglot Persistence) 전략이 일반적이다.

    - 트랜잭션 ACID
        - Atomicity: 전부 성공 또는 전부 실패(부분 반영 금지)
        - Consistency: 제약 조건과 비즈니스 규칙 일관성 유지
        - Isolation: 동시 실행 간 간섭 최소화(격리 수준별 이상 현상 차이)
        - Durability: 커밋 데이터의 장애 후 복구 보장
        - 정리: 정합성과 성능 사이 트레이드오프를 고려해 격리 수준을 선택한다.

    - 옵티마이저
        - SQL을 실행 계획으로 변환하고, 비용이 가장 낮은 계획을 선택한다.
        - 선택 기준: 통계(카디널리티), 인덱스 상태, 조인 순서, 정렬/집계 비용
        - 튜닝 포인트: 실행 계획 확인, 통계 최신화, 인덱스 재설계, 비효율 쿼리 개선

    - 쿠키/세션 vs JWT 전달 흐름과 보안
        - 쿠키/세션
            - 로그인 시 세션 ID를 쿠키로 발급, 이후 브라우저가 자동 전송
            - CSRF 위험이 높아 SameSite/CSRF 토큰/Origin 검증이 중요
        - JWT
            - 로그인 시 토큰 발급, 클라이언트가 Authorization 헤더로 전송
            - 쿠키 저장 시 CSRF 고려 필요, JS 저장소 사용 시 XSS 탈취 위험 증가
        - 공통 대응
            - XSS 방지를 위한 CSP, 입력 검증, 출력 인코딩, HttpOnly 설정

    - 로그아웃: 세션 삭제 vs 토큰 무효화
        - 세션 방식
            - 서버에서 세션 즉시 삭제 + 쿠키 만료 처리
            - 장점: 즉시 차단 가능 / 단점: 세션 저장소 운영 부담
        - JWT 방식
            - Refresh Token 서버 무효화(필수), Access Token은 짧은 TTL 또는 블랙리스트 활용
            - 장점: 확장성 우수 / 단점: Access Token 즉시 폐기 한계
        - 진짜 로그아웃 기준
            - 로그아웃 후 기존 자격증명으로 어떤 보호 API도 호출되지 않아야 한다.
