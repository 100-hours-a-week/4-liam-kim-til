# Class Notes(Cloud)

## 2026-05-27 (day 10)

### 강의

1. 인증 관련
    - 인증(Authentication)
        - 사용자가 누구인지 확인하는 과정
    - 인가(Authorization)
        - 인증된 사용자가 무엇을 할 수 있는지 결정하는 과정
    - 자격 증명 헤더
        - Authorization
            - Authorization: {scheme} {credentials}
            - 서버는 해당 헤더를 통해 사용자 신원을 확인한 뒤 권한 검사를 수행
            - 표준 헤더라 클라이언트/서버/프록시 환경에서 일관되게 동작
    - HTTP 인증 헤더 방식
        - Basic Authentication
            - 아이디:비밀번호를 Base64로 인코딩해 전달하는 방식
            - 인코딩일 뿐 암호화가 아니므로 HTTPS가 필수
            - 구현이 단순하지만 자격 증명 탈취 위험이 큼
        - Digest Authentication
            - 비밀번호 원문 대신 해시 기반 응답값을 주고받는 방식
            - nonce 등을 사용해 재전송 공격을 줄임
            - Basic보다 안전하지만 구현 복잡도가 높고 현재 사용 빈도는 낮은 편
        - Bearer Token
            - Authorization: Bearer {token} 형태로 토큰을 전달
            - 세션 상태를 크게 유지하지 않아도 되어 API/모바일/SPA 환경에 적합
            - 토큰 탈취 시 악용 가능하므로 만료시간/보관/전송 보안 설계가 중요

2. JWT
    - JWT(JSON Web Token)
        - 토큰 자체에 사용자 식별 정보와 클레임(claim)을 담는 형식
        - 일반적으로 Header.Payload.Signature 구조
    - 장점
        - 서버 세션 저장소 의존도를 낮춰 분산 환경에 유리
        - 토큰만으로 인증 정보를 빠르게 처리 가능
    - 단점
        - 토큰 길이가 길어져 네트워크 대역폭이 낭비될 수 있음
        - 발급 후 강제 무효화가 어렵기 때문에 별도 정책이 필요
        - Payload는 암호화가 아니므로 민감 정보 저장 금지
    - Access Token은 짧게, Refresh Token은 상대적으로 길게 운용
    - HTTPS 강제, 저장 위치(XSS/CSRF 위험) 고려 필수
    - 키 회전, 알고리즘 강제, 검증 실패 로깅이 필요

3. 인증 토큰 운영
    - Access Token
        - API 접근 권한을 증명하는 토큰
        - 수명이 짧고 만료 시 재발급 필요
    - Refresh Token
        - Access Token 만료 후 새 토큰 발급에 사용
        - 수명이 길어 보관/회수 정책이 중요
    - RTR(Refresh Token Rotation)
        - Refresh Token 사용 시마다 새 Refresh Token으로 교체
        - 이전 토큰 재사용 탐지가 쉬워 보안 강화에 유리
        - 상태 추적 로직이 필요해 구현 복잡도는 증가
    - DPoP(Demonstrating Proof of Possession)
        - 토큰만 제시하는 Bearer를 보완해, 클라이언트 키 소유 증명을 함께 요구
        - 토큰 탈취만으로는 재사용이 어려워져 보안성이 향상
        - 키 관리/서명 검증 로직이 추가되어 구현 난이도 상승

4. Layered Architecture
    - 역할을 계층별로 분리해 유지보수성과 테스트 용이성을 높이는 구조
    - Controller
        - HTTP 요청/응답 처리, 입력 검증, 응답 코드 관리
        - 비즈니스 로직은 service에 위임
    - Service
        - 핵심 비즈니스 로직 담당
        - 트랜잭션 경계와 도메인 규칙 처리
    - Repository
        - DB 접근(CRUD) 캡슐화
        - 영속성 기술 세부 구현을 분리
    - DTO
        - 계층 간 데이터 전달 객체
        - 요청/응답 스펙과 내부 도메인 모델 결합도 완화
    - Entity
        - 도메인 핵심 데이터와 상태 표현
        - ORM 환경에서 테이블 매핑 대상으로 사용
    - Controller -> Service -> Repository
    - DTO는 경계 데이터 전달, Entity는 도메인/영속성 중심으로 관리
