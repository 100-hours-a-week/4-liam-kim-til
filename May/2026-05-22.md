    ### 주제
    - HTTP의 Stateless 특성이 요청 처리 구조와 서버 확장성에 미치는 영향
    ### 메인 키워드
    - HTTP
        - HTTP는 애플리케이션 계층 프로토콜이며, 클라이언트-서버 간 요청/응답 모델로 동작한다.
        - 메시지는 Start Line + Header + Body로 구성된다.
        - 서버가 기본적으로 이전 요청 상태를 기억하지 않는다.
        - 버전별 특징
            - HTTP/1.1
                - 텍스트 기반, HOL(Head-of-Line) 블로킹 이슈, Keep-Alive로 연결 재사용.
            - HTTP/2
                - 바이너리 프레이밍
                    - 데이터를 사람이 읽는 텍스트가 아니라, 컴퓨터가 바로 처리하기 좋은 이진 형식(0과 1 단위의 구조화된 조각)으로 나눠 보내는 방식
                - 멀티플렉싱
                    - 하나의 TCP 연결 안에서 여러 요청/응답을 동시에 섞어서 보낼 수 있는 방식.
                - 헤더 압축(HPACK)
                    - 웹 요청은 헤더가 반복됨
                        - ex. User-Agent, Cookie, Accept
                    - 반복 전송하지 않고, 압축해서 보냄
            - HTTP/3
                - TCP 대신 QUIC(UDP 기반) 사용, 연결 설정 및 재전송 지연 개선.
    - Stateless
        - 각 요청은 독립적이며, 요청 하나만으로 처리 가능해야 한다.
        - 서버 메모리에 사용자별 상태를 강하게 묶어두지 않는다.
        - 장점
            - 수평 확장에 유리
                - 어떤 서버 인스턴스가 받아도 처리 가능
            - 배포 유연성 증가
                - 무중단 배포등 업데이트 시 세션 고정 의존성 감소
        - 단점
            - 사용자 상태(로그인 등)는 세션, 쿠키 등이 필요
            - 요청마다 인증 정보 전송으로 오버헤드 증가
    - 요청 처리 구조
        - Client -> DNS 조회 -> Load Balancer -> Web Server/Reverse Proxy -> WAS -> DB/Cache
    - 서버 확장성
        - 수직 확장(Scale-Up)
            - 서버 CPU, RAM 등을 증설
        - 수평 확장(Scale-Out)
            - 서버 인스턴스를 여러 대로 늘려 부하 분산.
        - Auto Scaling
            - CPU, 메모리, RPS, p95 응답시간 기준으로 증감
        - ~~데이터 계층 확장?~~
            - ~~Sharding~~
            - ~~Read Replica~~

    ### 확장 키워드
    - TCP(Transmission Control Protocol)
        - 연결 지향, 신뢰성 보장(순서 보장, 재전송, 흐름/혼잡 제어)
        - HTTP/1.1, HTTP/2의 기반 전송 프로토콜.
        - 데이터 무결성 보장이 필요한 웹 트랜잭션에 적합.
    - UDP(User Datagram Protocol)
        - 비연결형, 오버헤드 낮고 빠름
        - HTTP/3는 UDP 위 QUIC을 통해 신뢰성과 보안을 프로토콜 레벨에서 보완
        - 연결 설정 지연 감소, 모바일 네트워크 변경에 유리
            - 애플리케이션/상위 프로토콜이 신뢰성 제어를 직접 설계해야 함

    ### 결론
    - Stateless
        - "상태를 안 쓴다"가 아니라 "상태를 외부로 분리해 확장 가능한 구조를 만든다"는 설계
        - 서버를 "상태 저장소"가 아닌 "요청 처리기"로 설계
        - 서버를 독립적으로 만들어 확장성을 얻는 대신, 상태/일관성/보안을 체계적으로 운영
    - 장점
        - 트래픽 분산 유연성
            - 어떤 인스턴스가 요청을 받아도 처리 가능하므로 로드밸런싱 효율이 높아진다.
            - 특정 서버 장애 시 다른 서버로 즉시 우회하기 쉬워 가용성이 올라간다.
        - 확장성
            - 수평 확장에 유리하여 피크 시간대에 인스턴스를 빠르게 증설할 수 있다.
            - 오토스케일링과 결합 시 비용 대비 처리량 최적화가 가능하다.
        - 배포/운영 효율
            - 세션 고정(sticky session) 의존성이 낮아 무중단 배포와 롤링 업데이트가 단순해진다.
            - 장애 복구, 재시작, 교체 작업 시 사용자 요청 연속성을 유지하기 쉽다.
    - 단점
        - 상태 관리 분리 비용
            - 로그인 상태, 장바구니, 사용자 컨텍스트를 별도 저장소(세션 저장소, 캐시, DB)로 설계해야 한다.
            - 요청마다 인증 정보(JWT, 세션 ID 등)를 전달/검증하므로 검증 부하가 증가할 수 있다.
        - 데이터 일관성/복잡도
            - Redis 세션, 캐시, Read Replica를 함께 사용하면 일관성 정책(만료, 무효화, 재동기화)이 중요해진다.
            - 설계가 부실하면 캐시 불일치, 복제 지연, 인증 상태 불일치 같은 운영 이슈가 발생한다.
        - 보안 고려사항
            - 토큰 탈취, 재사용 공격 방지를 위해 만료 시간, 재발급, 폐기 전략이 필요하다.
            - HTTPS 강제, HttpOnly/Secure 쿠키, 키 회전 등 보안 설정이 함께 따라와야 한다.

    ### 회고
    - 수직적 확장, 수평적 확장이 영어로 Scale-Up, Out 인걸 처음 알았다….(짧은 영어…)
    - 개인적인 생각인데 일반적으로 말하는 HTTP의 Stateless 특성은 결국 서버 입장에서 Stateless 한 것에 불과하지 않았나 싶다. 때문에 HTTP/3(QUIC) 에서는 비연결형 통신인 UDP를 활용하여 클라이언트(ex. 모바일) 입장에서도 Stateless 한 연결을 추구한게 아닌가 싶다.
        - 모바일 같이 IP 주소가 바뀌거나 끊기는 환경에서도 문제없이 동작 및 스트리밍 할 수 있게 됨.
