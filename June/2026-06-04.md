# Class Notes(Cloud)

## 2026-06-04 (day 15)

### 강의

0. 백엔드 설계 방식
    1. 협업 방식 설계
        - 코드 규칙
            - 네이밍, 계층 분리, 패키지 구조, 테스트 작성 기준을 팀 단위로 합의
        - 주석 규칙
            - 왜 필요한 코드인지 중심으로 작성하고, 구현 상세는 코드로 드러나게 유지
        - 커밋 규칙
            - feat/fix/refactor/docs/test/chore 등 타입을 통일해 이력 추적성을 높임
        - 깃 전략
            - main/develop/feature 또는 trunk-based 중 하나를 선택하고 PR 기준을 명확히 함
        - 문서화 방식
            - API 명세, ERD, 아키텍처 다이어그램, 운영 가이드를 버전과 함께 관리
        - 커뮤니케이션 방식
            - 이슈 템플릿, PR 템플릿, 리뷰 체크리스트를 활용해 누락을 줄임
        - 회의 및 공유 방식
            - 데일리 스탠드업, 주간 회고, 장애 공유 템플릿으로 의사결정 맥락을 남김
    2. 도메인 요구사항 분석
        - 개발 우선순위 선정
            - 사용자 가치와 리스크를 기준으로 MVP 범위를 먼저 확정
        - 예상 사용자
            - B2C or B2B
            - 전체 사용자 수, 동시 접속자 수
            - 트래픽 피크 시간, 지역 분포, 기기 특성까지 확인해 인프라 가정을 세움
    3. RESTful API 설계
        - 리소스 중심 URI와 HTTP Method 의미를 일관되게 사용
        - 응답 코드/에러 포맷/페이지네이션/정렬/필터 규칙을 표준화
        - 버전 전략(v1, 헤더 버전 등)과 하위 호환 정책을 사전에 정의
    4. DB 스키마 설계
        - 정규화 수준, 인덱스 전략, FK 제약, 삭제 정책(soft/hard)을 명확히 설계
        - 조회 패턴을 기준으로 읽기 성능과 쓰기 성능의 균형을 맞춤
        - 트랜잭션 범위와 격리 수준을 도메인 규칙에 맞게 선택
    5. 코드 아키텍처 설계
        - Controller-Service-Repository 계층 책임을 분리하고 의존 방향을 고정
        - 공통 관심사(로깅, 인증, 예외 처리)는 필터/인터셉터/AOP로 분리
        - 모듈 경계를 기준으로 확장성과 테스트 용이성을 확보
1. 파일처리
    - 예시
        - Controller
            - ImageController
                - 업로드/조회/삭제 같은 HTTP 요청을 받고 검증 후 서비스로 위임
        - Service
            - ImageService
                - 일반적인 로직
                - 비즈니스 규칙(허용 확장자, 최대 용량, 중복 처리)을 수행
            - FileService
                - 파일 저장소 연동 로직(S3, 로컬 스토리지, CDN URL 생성)을 담당
            - ImageProccessor
                - 압축 이미지 변환?
                - 리사이징, 썸네일 생성, 포맷 변환(webp/jpeg) 같은 CPU 작업 전담
                - 분리 이유: 저장/비즈니스 로직과 이미지 처리 로직의 변경 주기가 달라 유지보수에 유리
        - Repository
            - ImageRepository
                - 메타데이터(파일명, 경로, 크기, MIME 타입, 업로더, 생성일) 영속화
        - Domain
            - ImageEntity
                - 파일의 상태(활성/삭제), 소유자, 접근 정책 같은 도메인 속성을 포함
2. 예외처리
    - BasicErrorController
        - 스프링 기본 에러 엔드포인트로, 공통 오류 응답의 최종 안전망 역할
    - ResponseStatusException
        - 특정 상황에서 빠르게 HTTP 상태 코드를 명시해 예외를 던질 때 사용
    - ExceptionHandler
        - @ControllerAdvice
            - MVC 컨트롤러 전역 예외를 한곳에서 처리해 중복 코드를 줄임
        - @RestControllerAdvice
            - JSON 응답 기반 전역 예외 처리에 적합(@ResponseBody 포함)
    - 운영 권장사항
        - 에러 코드, 사용자 메시지, 개발자 메시지, 추적 ID(traceId)를 분리해 응답
        - 비즈니스 예외와 시스템 예외를 구분하고 로그 레벨을 다르게 적용
3. 필터
    - 서블릿 컨테이너 레벨에서 디스패처 서블릿 전/후로 동작하는 공통 처리 단계
    - 스프링 MVC 진입 전 요청/응답을 가로채므로 인코딩, CORS, 로깅, 보안 헤더 처리에 적합
    - URL 패턴 기반으로 적용 범위를 제어 가능하며, 체인 순서(FilterChain)가 중요
4. 인터셉터
    - 스프링 MVC 레벨에서 컨트롤러 호출 전/후, 뷰 렌더링 이후를 제어하는 컴포넌트
    - HandlerMethod 정보를 활용할 수 있어 인증/인가, 감사 로깅, 실행 시간 측정에 유용
    - preHandle, postHandle, afterCompletion 생명주기를 이해하고 예외 상황까지 고려 필요
5. 문제
    - 인증과 인가는 어디에서 구현하는게 좋을까??
        - 인증
            - 1차로 필터(또는 Spring Security 필터 체인)에서 토큰 검증을 수행
            - 사용자 식별 정보를 SecurityContext에 저장해 이후 계층에서 재사용
        - 인가
            - URL 단위는 보안 설정으로, 비즈니스 단위는 서비스 계층/메서드 권한 검사로 분리
            - 컨트롤러 단일 지점보다 서비스 계층까지 방어선을 두는 것이 우회 방지에 유리
